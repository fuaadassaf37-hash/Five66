# الديوان العسكري — النسخة المدمجة (واجهة + سيرفر)

هذه نسخة مدموجة من أحدث واجهة (index.html) مع مشروع السيرفر، وفيها إصلاحان
جوهريان تمت إضافتهما بعد المراجعة:

## 1) تقليص حجم الواجهة من ~19 ميجابايت إلى ~7.3 ميجابايت (تصحيح كامل)

قسم "SHAM CASH" وصور الأشخاص في index.html كانا مضمَّنين كنص base64 مباشرة
داخل الكود (~11 ميجابايت) — وكان README يدّعي أن الفصل تم سابقاً لكنه لم
يكن مطبَّقاً فعلياً (الدوال كانت تقرأ البيانات المضمّنة ولا تُجري أي fetch).

تم الآن فعلياً:
- استخراج صور الأشخاص إلى `public/persons-photos.json` (ملف جديد).
- استخراج صور SHAM CASH إلى `public/shamcash-photos.json` (موجود مسبقاً ومتطابق).
- تحديث `loadPersonPhotos()` و `loadShamCashPhotos()` لتجلبا الملفات عبر
  `fetch` (مع cache: force-cache)، مع بقاء الكائنات المضمّنة الفارغة كاحتياطي.

النتيجة: تحميل أول أسرع بشكل كبير، خصوصاً داخل WebView الخاص بالتطبيق.

## 2) صلاحيات فعلية على مستوى السيرفر (admin مقابل viewer)

في النسخة السابقة، كان هناك نظام دخول داخل الواجهة (خيارات "admin" و"viewer")،
لكنه كان شكلياً بالكامل: أي شخص يعرف كلمة مرور Basic Auth المشتركة للموقع
(كلمة واحدة للجميع) كان يستطيع الكتابة عبر `/api/state` بغض النظر عمّا اختاره
في شاشة الدخول داخل الصفحة.

الآن يدعم السيرفر حسابين منفصلين فعلياً عبر `.env`:
- `ADMIN_USER` / `ADMIN_PASS` — صلاحية كاملة (قراءة + كتابة + نسخة احتياطية)
- `VIEWER_USER` / `VIEWER_PASS` — قراءة فقط؛ أي محاولة كتابة عبر
  `POST /api/state` أو `GET /api/backup` تُرفض بخطأ 403

⚠️ **قبل النشر**: افتح `.env` (أو انسخه من `.env.example`) وغيّر القيم
الافتراضية لكلمتي المرور — لا تُبقِ القيم الموجودة في `.env.example` كما هي.

> ملاحظة: شاشة تسجيل الدخول داخل الواجهة (five66/five1) ما زالت موجودة
> وتتحكم فقط بإظهار/إخفاء أزرار التعديل في الواجهة (تجربة استخدام)، لكن
> الحماية الحقيقية للبيانات أصبحت من طرف السيرفر عبر Basic Auth كما هو موضح
> أعلاه. يفضَّل مستقبلاً توحيد الحسابين (حساب واحد لكل مستخدم حقيقي) بدل
> وجود طبقتين منفصلتين من الدخول.

## 3) تنبيهات فورية عند فشل الاتصال بـ Supabase (تيليجرام)

**المشكلة:** ملف `data/state.json` هو الشبكة الآمنة الوحيدة عند تعطّل
Supabase مؤقتاً — لكن نظام ملفات Railway (وأي PaaS مشابه) **مؤقت**: يُمحى
عند كل إعادة نشر أو إعادة تشغيل. إن انقطع Supabase وتم الحفظ محلياً فقط،
ثم أُعيد نشر السيرفر قبل عودة الاتصال، تضيع تلك التعديلات نهائياً وبصمت.

**الحل المُضاف:** `db.js` يتتبّع الآن حالة كل عملية قراءة/كتابة مع
Supabase. عند أول فشل، وكل 15 دقيقة إن استمر الانقطاع، يُرسل السيرفر رسالة
فورية عبر بوت تيليجرام (`notify.js`) تُحذّر من عدم إعادة النشر/التشغيل
حتى تتأكد من عودة الاتصال. وعند التعافي، تصلك رسالة تأكيد أن المزامنة
سليمة ويمكن إعادة النشر بأمان.

**الإعداد** (اختياري لكن يُنصح به بشدة — راجع `.env.example`):
```
TELEGRAM_BOT_TOKEN=...   # من @BotFather
TELEGRAM_CHAT_ID=...     # من @myidbot أو @userinfobot
```
بدون ضبطهما، التنبيهات تُسجَّل في logs السيرفر فقط دون إرسال فعلي.

**للفحص اليدوي في أي وقت:** `GET /api/sync-status` (متاح لـ admin و
viewer) يعرض حالة الاتصال الحالية، وقت آخر نجاح/فشل، وعدد عمليات الحفظ
المحلية فقط منذ آخر انقطاع — راجعه قبل إعادة نشر السيرفر للتأكد أن كل
البيانات متزامنة فعلياً مع Supabase.

## محتويات الحزمة

```
project/
├── server.js              ← السيرفر (Express + Socket.io + صلاحيات admin/viewer)
├── db.js                  ← طبقة التخزين (Supabase أو ملف محلي) + تتبّع حالة الاتصال
├── notify.js               ← إرسال تنبيهات تيليجرام للمشرف
├── package.json
├── .env.example            ← انسخه إلى .env وعدّل القيم قبل التشغيل
├── supabase_setup.sql
└── public/
    ├── index.html          ← الواجهة (بعد تقليص الحجم)
    ├── shamcash-photos.json ← صور قسم SHAM CASH (منفصلة الآن)
    ├── manifest.json
    └── service-worker.js
```

## التشغيل

```bash
cp .env.example .env
# عدّل ADMIN_USER / ADMIN_PASS / VIEWER_USER / VIEWER_PASS في .env
npm install
npm start
```


## 4) إصلاحات إضافية على السيرفر (مراجعة أغسطس 2026)

- **حماية `/api/download/upload` بـ requireAdmin**: كان أي مستخدم بحساب
  المشاهدة (قراءة فقط) قادراً على رفع ملفات مؤقتة إلى ذاكرة السيرفر —
  الآن مقصور على المشرف كباقي عمليات الكتابة.
- **إصلاح تنزيل الملفات**: `/api/download/:token` كان يفك base64 الخام؛ لو
  وصلت القيمة بصيغة data URL (`data:...;base64,...`) كان الملف الناتج يتلف.
  الآن يُزال الترويسة تلقائياً إن وُجدت.
- **فحص صحة Supabase عند الإقلاع**: حالة `/api/sync-status` كانت تظهر
  "سليم" افتراضياً حتى أول عملية فعلية؛ الآن يُجرى `readAll()` فور بدء
  التشغيل فتظهر الحالة الحقيقية (مع تنبيه تيليجرام إن كان الاتصال معطلاً).
